# SEC-027 — Encerrar a sessão quando um refresh token já trocado for reutilizado

## Entrega
- `auth_refresh_tokens` ganha `usado_em`, com migração em `ensure_schema_updates`, conferida num banco da versão atual da `dev`, rodando duas vezes.
- **Rotação atômica** (`trocar_refresh_token`): um `UPDATE ... WHERE token_hash = ? AND usado_em IS NULL AND expires_at > agora` marca o token **antes** de emitir o par novo, e só o pedido que consegue marcar recebe tokens. Com pedidos simultâneos, um vence e o outro cai no reuso. O token antigo e o novo nunca valem ao mesmo tempo.
- **Reuso:** se o refresh enviado já foi trocado e ainda não venceu, a API nega (401, a mesma mensagem de refresh inválido), encerra todas as sessões do dono (`encerrar_sessoes`, que incrementa `token_version` e apaga todos os refreshes) e grava `refresh_reutilizado` na trilha.
- **Logout:** continua apagando o refresh enviado, mas só se ele for do próprio usuário. Assim ninguém apaga o refresh de outra conta, nem a prova de um reuso.
- **Refresh trocado e vencido:** reenviá-lo dá só 401, sem encerrar sessões, porque ele não serviria mais.
- **Limpeza:** os refreshes trocados vencem e são apagados pela limpeza do start (SEC-014).

| Critério de aceite | Prova |
|---|---|
| Refresh já rotacionado e reenviado: a API nega e encerra todas as sessões do usuário | `test_reuso_de_refresh_trocado_nega_e_encerra_todas_as_sessoes`: 401; o access e o refresh do dono e de outra sessão do mesmo usuário deixam de valer; nenhum refresh do usuário sobra no banco |
| O uso legítimo (um refresh por vez) continua funcionando | `test_uso_legitimo_um_refresh_por_vez_continua_funcionando` (três rotações seguidas) e os testes de refresh existentes, sem alteração |
| O evento fica no log de auditoria | `test_reuso_fica_na_auditoria` (`refresh_reutilizado`, com o usuário) |

Também cobertos: o reuso não afeta outro usuário; um refresh desconhecido continua dando 401 sem encerrar nada; pedidos simultâneos (`test_pedidos_simultaneos_so_um_recebe_o_par_novo`); refresh trocado e vencido; logout com refresh de outra conta.

## Testes
- **Novos:** 8 testes em `tests/integration/test_seguranca_reuso_refresh.py`; antes da mudança, os 2 de reuso falhavam.
- **Suíte completa:** 1090 passaram, 3 pulados, cobertura 96%. Rodada numa cópia sem o arquivo de segredos local.
- **Mutação:** sem o encerramento no reuso, 2 testes novos falham; sem a condição `usado_em IS NULL` na troca atômica, 3 falham.

## Segurança
- `/security-audit diff dev` em 2026-11-08: os 7 scanners com status `ok`. **Nenhum achado novo.**
- `/code-review` (medium):
  - **Corrigidos:**
    - a corrida entre pedidos simultâneos, com a troca atômica;
    - a janela em que o token antigo e o novo valiam juntos;
    - o reuso de um refresh vencido encerrava sessões;
    - o logout apagava o refresh de qualquer conta;
    - a consulta duplicada.
  - **Sem mudança:**
    - não há janela de tolerância para o cliente que perde a resposta e repete o refresh. Ele cai no reuso, como pede o critério, e o ADR-0004 e a nota local recomendam uma renovação por vez;
    - os refreshes trocados ficam até vencer, e a limpeza do start os apaga.
- Detecção de reuso de refresh rotativo (OWASP API2:2023, CWE-613). O R-011 passa a mitigado, e o ADR-0004 registra a contrapartida: dois refreshes simultâneos do mesmo token encerram as sessões do próprio usuário.
