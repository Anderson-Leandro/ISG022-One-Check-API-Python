## N3 — Criação de checklist sem autorização

**Causa:** `POST /contratos/{id}/checklists` usava só `get_current_user` e aceitava qualquer `vistoriador_id`. Como `_assert_vistoriador` compara o usuário com o vistoriador do checklist, quem se nomeasse vistoriador podia preencher e submeter. Se fosse também o locatário do contrato, aceitava a própria vistoria.

**Pilares:** Integridade, Não-repúdio · **STRIDE:** Tampering, Elevation of privilege · **OWASP API5 / CWE-862** · **Princípios violados:** mediação completa, separação de deveres.

| Arquivo | Mudança |
|---|---|
| `app/routers/contratos.py` | `create_checklist` passa a exigir `require_roles("admin", "gestor")` e contrato `ativo`. `vistoriador_id` precisa ser um usuário **ativo com perfil `vistoriador`**; senão a resposta é `fail("Vistoriador não encontrado")`, o que também resolve o item 3. |
| `app/routers/checklists.py` | `_assert_pode_aceitar` nega (403) quando quem aceita ou rejeita é o próprio vistoriador do checklist. Isso cobre dados antigos e mudanças de perfil posteriores. |

**Testes** — `tests/integration/test_seguranca_checklist_autorizacao.py` (13):
- **Quem pode criar:** locatária se nomeando vistoriadora → 403; locatária em contrato alheio → 403; vistoriador e visualizador → 403; gestor → ok.
- **Validação:** vistoriador inexistente → falha sem 500 e sem registro criado; usuário sem perfil vistoriador, admin como vistoriador ou vistoriador inativo → falha; contrato encerrado → falha.
- **Separação de deveres:** quem vistoriou não aceita nem rejeita; outro aprovador aceita normalmente.

## N4 — Gestor se promovendo a admin

**Causa:** em `/usuarios/{id}`, as rotas só exigiam `require_roles("admin", "gestor")`, sem considerar quem era o **alvo**. O campo `role` aceitava qualquer texto. Com isso, o gestor podia:
- se promover a admin e promover outros usuários;
- criar admins;
- trocar senha e e-mail de um admin;
- zerar o MFA de um admin ou **definir um segredo TOTP que ele mesmo conhecia**.

**Pilar:** Autenticidade · **STRIDE:** Elevation of privilege · **CWE-269** · **Princípio violado:** menor privilégio.

| Arquivo | Mudança |
|---|---|
| `app/auth.py` | Novos conjuntos `ROLES` (perfis válidos) e `PRIVILEGED_ROLES` (`admin`, `gestor`). |
| `app/routers/usuarios.py` | `_assert_pode_gerenciar(current, alvo)`: nega (403) quando o alvo é a própria conta, que deve usar `/usuarios/me`, e quando o alvo é admin/gestor e quem age não é admin. Aplicado em `PUT /{id}`, `DELETE /{id}`, `POST /{id}/mfa/setup`, `POST /{id}/mfa/enable` (e `/habilitar`), `DELETE /{id}/mfa` (e `POST /desabilitar`). |
| `app/routers/usuarios.py` | `_assert_pode_atribuir(current, role)`: só admin atribui `admin`/`gestor`, ao criar ou ao editar. Perfil fora de `ROLES` → `fail("Perfil inválido")`. As validações rodam **antes** de qualquer alteração no objeto. |
| `app/routers/usuarios.py` | Promover alguém a um perfil com MFA obrigatório liga `mfa_enabled`. Antes, um locatário promovido a gestor continuava sem MFA. |

**Testes** — `tests/integration/test_seguranca_gestao_usuarios.py` (23):
- **Gestor não escala:** não se promove; não promove outros a admin/gestor; não troca senha nem e-mail de admin; não altera outro gestor; não reseta o MFA de admin (pelas duas rotas); não define o segredo MFA de admin; não vê o setup de MFA de admin; não desativa admin; não cria admin nem gestor.
- **Perfis:** perfil inexistente é recusado ao editar e ao criar.
- **Própria conta:** o admin não altera a própria senha nem reseta o próprio MFA por `/{id}`.
- **Caminhos legítimos:** gestor edita locatário; gestor cria vistoriador (com MFA exigido); admin promove locatário a gestor (o MFA passa a ser exigido); admin gerencia gestor.

## N5 — Desativar o MFA sem reautenticação

**Causa:** `POST /auth/mfa/desabilitar` e `DELETE /usuarios/me/mfa` desligavam o MFA só com o access token. Isso valia até para admin, gestor e vistoriador, em que o MFA é obrigatório. Além disso, os resets feitos por admin gravavam `mfa_enabled=False`, o que liberava login **sem segundo fator** para esses perfis.

**Pilar:** Autenticidade · **STRIDE:** Spoofing, Elevation of privilege · **CWE-306 / CWE-308** · **Princípios violados:** fail secure, defesa em profundidade.

| Arquivo | Mudança |
|---|---|
| `app/schemas.py` | Novo `MfaDisableSelfRequest` com `senha` obrigatória e `codigo` opcional. |
| `app/auth.py` | `mfa_self_disable_error()` exige a senha e, se houver autenticador, o código TOTP atual. `reset_mfa()` limpa o segredo ativo e o pendente e mantém `mfa_enabled=True` em perfis obrigatórios, o que força nova configuração no próximo login. |
| `app/routers/auth_router.py`, `app/routers/usuarios.py` | `/auth/mfa/desabilitar` e `DELETE /usuarios/me/mfa`: perfis obrigatórios recebem 403; perfis opcionais precisam reautenticar. Corpo ausente → 422. |
| `app/routers/auth_router.py` | `/auth/mfa/disable` (admin) usa `reset_mfa()` e não aceita a própria conta: outro admin precisa fazer o reset. |
| `app/routers/usuarios.py` | `DELETE /{id}/mfa` usa `reset_mfa()`. `PUT /{id}` com `mfa_enabled: false` em perfil obrigatório → `fail("MFA é obrigatório para este perfil")`. |

**Testes** — `tests/integration/test_seguranca_mfa_desativacao.py` (21):
- **Perfis obrigatórios:** admin, gestor e vistoriador não desativam o próprio MFA nem com senha e código corretos (pelas duas rotas).
- **Perfis opcionais:** token roubado sem corpo → 422; senha errada, código ausente ou código errado → falha; senha e código corretos → desativa; MFA habilitado sem autenticador desativa só com a senha.
- **Reset por admin:** em perfil obrigatório, o próximo login devolve `mfa_setup_required` e nenhum `access_token` (pelas duas rotas e por `/auth/mfa/disable`); o admin não reseta o próprio MFA; `PUT` não desliga MFA de perfil obrigatório; em perfil opcional, o reset desliga.

## Impacto no front e na API
| Mudança | O que o front precisa fazer |
|---|---|
| `POST /auth/mfa/desabilitar` e `DELETE /usuarios/me/mfa` exigem `{"senha", "codigo"}`; perfis obrigatórios recebem 403 | Pedir a senha e o código na tela de desativar MFA e escondê-la para admin, gestor e vistoriador |
| `PUT/DELETE /usuarios/{id}` e as rotas `/usuarios/{id}/mfa/*` com o **próprio** id → 403 | Na tela de usuários, a própria conta deve usar `/usuarios/me` e `/usuarios/me/senha` |
| O gestor não edita, desativa nem reseta contas admin/gestor, nem atribui esses perfis | Esconder essas ações para o gestor e limitar o seletor de perfil |
| `POST /contratos/{id}/checklists` só para admin/gestor, com vistoriador de perfil `vistoriador` e contrato ativo | Listar só vistoriadores no seletor |
| O reset de MFA de perfil obrigatório mantém `mfa_enabled=true` | Nada: no próximo login o usuário recebe `mfa_setup_required` |

## Riscos residuais
- `POST /usuarios/{id}/mfa/setup` + `enable` ainda deixam um **admin** escolher e conhecer o segredo TOTP de outro usuário. O ideal é que o admin só resete e o próprio usuário configure no próximo login.
- Ainda não há rate limit no login nem no `/mfa/verify` (**N6**), e a reautenticação de N5 também é alvo de força bruta da senha.
- Pendentes desta fila: **item 1** (`GET /auth/mfa/setup` sobrescreve o segredo ativo), **item 2** (listagem de usuários com CPF), **item 6** (BOLA em `/problemas/{id}`), **N6**, **N7** e **N8**.
